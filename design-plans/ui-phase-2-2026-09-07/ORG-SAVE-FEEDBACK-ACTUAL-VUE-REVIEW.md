## 依据与范围

沿实际 App → NavigationShell → OrganizationAdminCenter 的组织概览入口，基线是前批
组织表单提案。现有 `submit` 在 PATCH 成功后执行 `load`；`load` 捕获读取错误不向上
抛出已识别的 API 错误，因此 submit 随后覆盖读取错误文案和 requestId。双端本地500、
403对照均复现通用“操作已完成并写入审计”覆盖读取结果，不把它误称为保存请求失败。

产品总纲对应组织写入原因、幂等、版本和审计边界。实际 route/service/repository 核对
表明 PATCH 成功返回 id/version/updated_at，而原M06 E2E对该路径不区分方法返回全profile。
本批从 repository 的 updateProfile.result AST 提取真实字段表达式，使用原profile的
id/version/日期作为本地输入，不虚构全资料写入返回。时间只是样例时钟，不证明真实更新。

## 提案

- 仅审核宿主分开显示“资料已保存”与“页面正在更新 / 已更新 / 暂未更新”。
- 保存、读取编号分别位于原生 details 中；失败时保留既有错误区及读取编号。
- 普通读取失败说明下方只读资料来自上次读取；权限拒绝仍撤下资料和表单，指向既有
  重新加载入口，不通过文案恢复权限或泄露已撤下的组织名称。
- 按每次 load 的实际返回判断，不使用可能残留的 lastReadFailureStatus。
- 资料写入反馈随组织/路由切换及停用清除；失去归属的写入不启动新页面读取，过期读取
  不发表回执。其他 submit 分支保留原文案和行为；本批不顺手修复其他写入链。

原字段约束、PATCH 地址/方法/参数、expected_version、幂等头、原因、权限及服务端事务
不变。原成功后清空表单并在成功读取时重新填充的规则保持；失败后表单可能只有空原因，
没有擅自恢复草稿或禁用再次保存。先前草稿策略问题仍待用户决定。
