## 1. 目标与范围

以现有业务能力和历史 Signal Ledger 2.1 实现为功能基线，重新设计全部页面的布局、视觉、真实按钮和弹窗状态，完成 Vue 实现与可追溯验收，最终交付用户能够逐页审阅的完整审核包。历史部署记录不作为本次线上状态证明。

当前蓝图中的信号账页体系（纸张底色、墨色正文、朱砂主行动、零圆角、无装饰阴影与渐变、横向模块导航）是现有工程参考，不是用户对第二阶段设计的预先通过。按用户“以前所有 UI、布局都不要，重新设计”的要求，73 条路由全部重新评估信息架构与构图；保留业务功能与合同，不默认保留旧布局，也不因核心页已有测试而豁免重新设计。W01 必须先交付具有结构差异的代表方案及旧版对照，经用户选定后同步设计规范，再开展全站实施。不得将换色、覆盖 CSS 或所有页面套相同模板作为逐页设计完成依据；每页必须说明自己的主要任务、信息顺序和动作层级。

本次制定计划只调整计划文档。实施阶段范围为前端页面、组件、样式、交互测试、验收工具和相关文档。保持既有字段、请求方法、权限、业务规则、任务语义和持久化契约；拟议布局所需事实不存在时，记录数据缺口，不添加假指标或自行扩展后端。没有新增依赖、服务、数据库迁移或环境变量的默认需求。

页面逐项分工及验收见 [PAGES.md](PAGES.md)，具体领任务、审图、复测和交接见 [EXECUTION.md](EXECUTION.md)。已有产物以 [PROGRESS.md](PROGRESS.md) 和实际文件为准，其余仍待产出；不能引用计划或未验证草稿作为“实现完成”证据。

## 4. 每页必须先完成的设计规格

每页规格必须包含以下十项，缺少任一项不能进入该页编码：

1. 用户角色、当前业务范围、进入来源、离开/返回位置。
2. 一个主要任务及已有 API/字段出处；区分事实、计算值、缺失状态与辅助解释。
3. 桌面构图：标题与主行动、首屏重点、列表/详情/说明的顺序、滚动容器。
4. 移动构图：摘要折叠、主次操作、表格字段化、详情返回、固定操作区与安全间距。
5. 所有 actionId 的名称、层级、可见/禁用条件和结果反馈；页面级全局创建与局部创建避免重复突出。
6. 弹窗入口、字段及必填项、校验、取消、失败重试、提交中和成功后行为。
7. 加载、空、搜索无结果、错误、离线、过期、无权限、受阻、恢复等适用状态；不适用项写理由。
8. 搜索/筛选/分页/选中/排序的现有存储位置，刷新和跨组织切换的行为；不得擅自新增持久化。
9. 390、768、1024、1440px 的排版说明及断点邻界检查；三主题和两种密度的适用规则。
10. 可执行验收步骤、期望结果、图路径与审核负责人。

效果规范：正文和输入控件不小于 16px，元数据不小于 13px，可交互热区不小于 44×44px。颜色令牌、文本状态、焦点环、loading 和错误信息一致。动效仅用于动作反馈与层级切换，优先 opacity/transform，遵守 reduced-motion；不对长表格行逐条入场。计划提出的任何新动效时长在 W01 评估确认后写入统一令牌，不逐页随意添加。

布局不得因长中文、长商品名、零数据、多页数据、200% 缩放、移动软键盘或固定底栏发生遮挡。数据表可保留有标签的局部横向滚动，但整个页面不能溢出。信息排序只调整视觉位置；数据排序、推荐资格、价格与利润算法继续来自当前合同。

## 6. 按钮与弹窗逐项验收

### 动作清单

actionId 使用稳定语义键，例如 `task.detail.assign`；历史扫描编号保留为 sourceInventoryIds，源码行号只辅助定位。每个动作记录 routeId、组件、触发条件、角色/capability、真实 handler、现有 API 契约引用、输入/输出、成功与失败表现、是否有外部副作用、测试文件和结果证据。

步骤为：静态扫描 → 查 handler 与 API → 遍历动态菜单/批量态/空态 → 合并重复渲染 → 补 role=button、链接动作、菜单项 → 校对无孤立 handler、无漏记关键入口。纯跳转与写入分开。每个按钮均审核默认/悬停/聚焦/按下/禁用/处理中六态；没有异步行为时“处理中”记不适用理由。

同一个视觉组件只需一套六态放大图，但每个业务动作仍要独立证明名称、位置、可达性、禁用理由和调用结果。共享组件测试不能代替每个调用方的业务验收。危险动作不依据中文关键词推断，必须追踪真实 handler。

### 弹窗清单

每个弹窗及动态变体都要桌面/移动打开态图；补充校验失败、提交中、请求失败、成功关闭/保留等适用图。每个调用方核查：触发→首焦点→Tab/Shift+Tab循环→Escape/取消→焦点归还→重复提交保护→成功后的原页同步。复用 `useModalDialog` 已有行为，关闭时保留/丢弃草稿遵循当前页合同，不在视觉重构中统一改变。

弹窗长内容可滚动且标题、错误提示与操作区可达；移动键盘不能盖住当前输入或确认按钮。确认影响只使用已有事实，无明确影响人数、任务数时不编数字；不可逆操作、原因、范围及后果必须明确。密钥只展示已允许的掩码，图中不能出现原始凭证。

## 9. 提交、部署与回退

本轮计划文件可以单独提交；实际编码时记录当时分支、HEAD和工作树，仅暂存该工作包文件。代码/API/配置没有改变的计划提交无需发布应用，也不需要重启。

发布时读取线上真实SHA作为base，不固定沿用本计划基线。确保本地main、origin/main、发布清单head一致，工作树干净；精确列出区间提交与路径，通过 `npm run verify:release-ownership` 后执行 `python scripts/deploy-baota.py`。沿用标准UTF-8路径，不再尝试GBK名称转换。

当前部署器并非纯前端上传：其 main 链会上传运行包、通过宝塔停止 Node、执行既有迁移白名单，再切换目录并公开验证。即使本阶段没有新增 SQL，也必须在发布前确认白名单每项的生产执行记录、是否存在待执行迁移及维护窗口；发现新增或未授权迁移先暂停，不把历史“允许迁移”扩大为任意迁移授权。不假设无服务中断，不虚构 `--frontend-only` 或 `--rollback` 参数。对应预检列入 EXECUTION 的发布任务。

部署前检查脚本当前回退边界：固定目录切换过程有恢复逻辑，但 `verify_public` 失败不等同于所有运行包、环境配置和数据库都自动恢复。必须为当前版本保留可恢复的运行包与受限配置备份，记录原SHA；在生产健康与关键页面通过前不得删除恢复材料。不得把前端回退描述成数据库自动回退。

如果部署公开验证失败，核对目录是否切换、环境是否变更、服务是否启动，再通过已授权宝塔管理能力恢复已知稳定运行包及必要配置，并检查live/ready/available/version。若当前部署器无法满足保留恢复材料的要求，在发布前补相应最小修复及测试；不能先发后补。本阶段正常不含新数据库迁移，现有白名单执行记录仍需核对。

Node（含API/Worker）与Python按部署器/宝塔实际变更重启，Nginx配置有变更才在语法检查后reload。不创建额外站点、candidate服务、current/releases目录或新的后台管理能力。图稿与测试材料不进入生产静态包，既有服务目录仍为frontend/backend/python/config/runtime/backups。
