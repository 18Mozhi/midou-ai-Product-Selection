# 必需来源熔断时保留采集尝试

生产真实观测发现 Amazon 来源熔断后，队列仍领取任务，执行器在发起请求前返回 `source_circuit_open`；这些领取会消耗四次尝试并最终进入死信。一次搜索页健康探测成功也不代表所有商品详情可访问。

## 领取规则

Worker 选择 queued 候选及按主键、组织、工作区复核时，都排除同任务、同组织、同工作区内存在必需子查询且其来源熔断 open 的任务。任务继续保持 queued，未领取就不创建 attempt、租约、领取事件或公平轮次；不通过反向扣减尝试、篡改终态或额外重放实现。

可选来源熔断不阻止其他必需来源运行。没有熔断记录或已 closed 的来源保持原行为。仅保留执行器已有的 1688 `acceptance_run: true` 布尔值例外；缺失、null、字符串 true、false 或其他来源不能使用这个例外。

本规则不清空熔断、不自动启用来源、不绕过 robots、登录、验证码或访问拒绝。来源按既有审计恢复后，等待任务由正常轮询领取；来源检查后的并发变化仍由执行器原有检查处理。四次上限、实际失败退避、死信、过期租约恢复、显式优先级及 20 次后 FIFO 轮次不变。已耗尽或其他历史终态不在本次补偿范围。

## 验证与运维

定向状态机与调度测试覆盖未领取不写 attempt/租约/事件、候选失效、事务回滚、范围约束和公平轮次。真实 MySQL 5.7 使用 SELECT 派生数据验证 13 个边界案例，不建立测试表或修改业务数据。生产默认工作区只读抽查四个 queued 任务，全部被正确识别为等待来源，尝试次数分别为 2、0、2、2，查询耗时 6ms。

无数据库迁移、新 API 字段、事件、依赖、环境变量、并发或超时配置。OpenAPI 仅说明既有 attempt_count 语义；前端和 Python 合同无变化。通过正式宝塔部署脚本发布后需重启既有 Node 项目 ai选品，让 Worker 加载领取规则；不新增服务。上线后检查熔断任务的 attempt_count 是否保持、健康来源任务是否继续，以及来源真实恢复后的自然领取。队列不耗尽不能代替每日至少 100 个整链商品验收。
