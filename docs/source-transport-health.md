# Amazon 请求身份与 1688 LAN 健康检查

## 生产依据

2026-10-18，后续链路优先调度生效后，先前等待的 9 个详情、竞品和找货任务实际被领取，但受到来源熔断阻断。Amazon 最近连续五次 network_error，标准健康页使用旧 Chrome 请求身份时仍失败；同一公开爬虫策略允许的地址，使用 ScoutOpsPublicCrawler/1.0 得到 HTTP 200、可解析商品。单次成功不能证明永久可用，也不能据此断言历史错误的唯一原因。

1688 LAN 节点真实 POST 返回 success、items 等原有响应字段，样本十条均可解析；来源健康却没有实际记录，注册的是旧浏览器占位健康实现。不能以服务可访问为由直接清空熔断，必须补齐真实健康及审计流程。

## 实现

- Amazon 适配器 v10 的页面请求与 robots 检查使用同一 PUBLIC_CRAWLER_USER_AGENT，即 ScoutOpsPublicCrawler/1.0。删除该适配器旧 Chrome 冒用头；不切换代理、不绕过 robots、验证页、鉴权或限流。解析字段版本仍为 amazon-public-product-v5。
- 将既有 LAN 客户端和解析器移到 packages/provider-sources，Worker 原路径只转导出，同一套六节点、固定鉴权、字段、60 条上限、字节限制、故障切换及禁止重定向逻辑继续复用，不复制实现。
- API 注册来源时，仅在已有 LAN_1688_TOKEN 配置存在时使用 1688-lan-health-adapter-v1。真实健康检查复用同一 LAN 客户端，对用户提供的固定 Amazon 示例图执行图搜并校验原响应格式。健康结果不返回候选、不持久化商品或供应商事实、不计产出；空合法响应也只能证明接口可工作。
- 无 token 时保留原浏览器验证 gate。旧浏览器采集入口仍由原适配器处理，Worker 的正式图搜继续使用原 LAN 执行路径，不用健康样本替换业务图片或结果。
- Registry 增加内部可选、严格校验的逐适配器健康期限；API 的 1688 使用已有 LAN_1688_TIMEOUT_MS，同时取来源 timeout_ms 较小值。其他来源继续使用 PROVIDER_ADAPTER_HEALTH_TIMEOUT_MS。没有新增环境变量、HTTP 参数、数据库迁移、依赖或 Python 变化。
- 所有 token 均只在后端配置及 LAN 请求头中使用；来源列表、健康结果和规范化事实不携带凭证。

## 验证及运行

tests/unit/source-transport-health.test.mjs 覆盖请求身份一致、共享实现、真实请求结构、健康不泄露候选/凭证、规范化溯源、未配置 gate、失败和取消、逐来源超时及非法期限拒绝。既有 LAN 图片、60 条响应、六节点、重定向、证据和 Amazon 结构/验证页保护测试保留。

ProviderAdapterCenter 使用既有健康 POST 和待完成状态，没有额外的短期限写请求计时器；API 响应字段不变，因此前端无需增加字段或配置。OpenAPI 只补充既有健康行为说明。config/env.example 同步既有两个超时的适用范围，实际环境值未改变。

正式部署后重启唯一宝塔 Node 项目 ai选品。先用现有 ProviderAdapterService 执行真实健康检查，再由 CrawlerSchedulerRepository 审核晚于熔断时间的 ready 记录并恢复；健康接口本身不会启用来源、批准条款或清空熔断。没有可自动放行的模拟健康结果。商品业务任务仍须独立采集和验收，日百品未完成。

## 六节点健康覆盖修复（2026-10-18）

生产只读核对发现来源timeout_ms=20000，LAN_1688_TIMEOUT_MS=45000。Registry原本正确保留较小的20秒总期限，但健康实现复用串行collect：首节点尚未达到45秒单次期限，外层就取消全部操作，后续节点可能从未被尝试。API重启还会重置内存轮转位置。不能把这个结果当作六台设备都不可用，也不通过增大时限掩盖。

1688-lan-health-adapter-v2改用同一客户端的checkPoolHealth：在原总期限内同时检查221–226六个固定节点，每节点最多一个请求；任何节点返回通过原解析器的合法响应，即证明池至少一个节点可用。健康不代表六个节点全部正常。成功后取消其余请求，并等待本轮资源释放；全失败、全部鉴权失败、全部结构异常或调用取消均不生成ready。全失败保留已知非重试错误优先。健康响应不包含候选、授权值或原始正文，不写入商品或供应商事实。

请求构造、固定Bearer鉴权、四个JSON字段、60条与2MB上限、禁止重定向以及响应解析统一在requestEndpoint中复用。正式业务collect仍按原轮转顺序串行故障切换，401/403及不合法响应仍失败关闭。健康并发只覆盖已有六台用户指定设备，不增加主机、端口或对外接口。

回归用更小的100ms总预算和1000ms单节点预算模拟同一边界：前五节点一直等待，第六节点可用；旧函数超时，新函数真实校验第六响应后返回ready并取消五个请求。另验证所有占用节点不重复发送、取消释放六个占用后可继续正常采集，以及原协议、鉴权、数据上限和取消边界。受控结果不能证明当前六台实机或日百品已通过。

没有新增环境变量、API字段、数据库、依赖、权限或Python变化。总期限仍为min(来源timeout_ms, LAN_1688_TIMEOUT_MS)，其他来源继续使用原健康上限；真实环境值不改。既有变量若调整需由宝塔重新加载API/Worker，来源记录超时由原后台动态读取。本次代码经本地deploy-baota.py发布并由宝塔切换现有服务后生效。观察自然健康审计及原熔断恢复；禁止手动强制放行，真实货源和每日100个完成商品须另验。

## 2026-10-19 LAN HTTP429 限流归属

05:07从生产主机按用户既有图搜协议只读诊断六个固定节点：221返回503，222–226返回429。未持久化样本报价，未改来源状态。实际响应说明当时接口拒绝请求，不能将全部失败描述为网络断连，也不能据此认定设备永久故障。

共享客户端现在将HTTP429识别为既有 rate_limited、retryable=true，并释放响应体；业务仍在六节点内顺序故障切换，真实成功优先。全部失败时，已经观察到的429不会被后续普通503/连接错误覆盖；401/403、格式失败等不可重试错误仍立即失败关闭。健康池全部失败时仍优先不可重试错误，其次限流，再其次普通依赖错误；实际合法响应、取消和总预算不变。

Worker已有 rate_limited 消费分支生成未来五分钟的 rateLimitResetAt，任务状态机沿用原限流等待；不新增长重试、并发、节点、配置或绕过设备限流。API健康结果沿用现有errorCode字段，前端、Python任务、报价规范化与评分数据均不改；原network_error历史不回写，未强制恢复熔断。

21项最小测试覆盖全429、429后503、健康混合故障、鉴权优先、健康节点回退、响应体释放和实际Worker五分钟等待、零供应商事实写入。新增永久测试，无验证专用临时脚本/服务；脱敏运行诊断回执保留于 .artifacts/selection-production-20261018/lan-six-node-current-diagnostic.json。此修复不是六节点恢复或日百品验收。正式按deploy-baota.py发布并由宝塔重启Node以加载API/Worker共享客户端；没有新增调节项，原设备、限流及来源恢复策略仍生效。
