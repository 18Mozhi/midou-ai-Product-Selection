# M04-05 竞品监控架构

## 边界

`amazon_product` 的代码目录定义固定为 `enabled/public_page/manual` 与 `amazon-structured-product-v2`。因此全新数据库在平台超级管理员完成目录同步后即可创建真实采集任务，不依赖“先启动旧版本、再执行启用迁移”的部署时序。

本模块支持两条真实入口：外部 Provider 提交带证据的完整快照；普通成员提交 Amazon 商品 URL 后，由已启用的 `amazon_product` 公开页面适配器采集。后者不需要官方 API，也不以示例值补齐页面没有披露的字段。Amazon Adapter v4 对无代理直连使用 Node 原生 HTTPS，避免 Undici 被目标站误判为 503；配置专用 Provider 代理时仍遵循代理传输。Parser v2 优先读取页面中的 Schema.org Product JSON-LD，以 SKU/商品 URL 确认 ASIN，并保留结构化字段路径与原始 JSON-LD 证据；仅在页面没有有效 Product 结构化数据时回退到既有语义 HTML 标记。HTML 价格币种按响应中的 ISO 代码或明确货币符号提取，无法确认时保持为空，不把访问区域返回的 CNY 强制写成 USD。为避免代理瞬时返回不完整 HTML 导致持续监控被误停，首次 `source_changed` 会在同一超时边界内以相同传输重读一次；第二次仍无法形成真实商品记录才以 `source_changed` 失败关闭并触发来源停用。竞品身份按组织、工作区、市场、来源站点和外部商品 ID 唯一。

重复采集使用任务级原始证据键与稳定 ASIN 记录键：同一任务重试保持幂等，不同任务观测到同一 ASIN 时创建下一版 `normalized_records`，旧版标记为 `superseded` 且新版记录 `supersedes_record_id`。竞品主体仍按 ASIN 去重，下游每次有效观测生成新快照。

## 数据流

`competitors` 保存身份、软删除状态和当前指针；`competitor_snapshots` 保存不可变快照。公开页采集先进入现有 `collection_tasks`，`CoreCollectionProjectionWorker` 把规范记录投影为快照，再由竞品比较 Worker 生成字段变化。达到显式阈值时，`competitor_alerts` 同时记录通知和任务的 `queued` 状态，并写 `competitor_outbox`。统一 Node Worker 的业务任务投影器按 `change_id` 幂等创建 `selection_verification` 任务，把同一个告警 ID 转入通用 `outbox_events`；通知 outbox 发布站内通知后分别把 `task_status` 更新为 `created`、`notification_status` 更新为 `delivered`，通知偏好阻止投递时明确记为 `failed`，不会永久伪装成排队中。

公开页快照始终保存采集时间、来源状态、原始证据和商品地址；价格、货币、排名、评论数、评分和库存按页面真实披露保存，可为空但不能用零代替。首个快照建立基线，不制造变化。数值阈值按绝对变化量判断，库存仅支持任意变化或变为缺货。

竞品快照完成比较后会重新排队其关联机会的自动质量评估。市场与竞争输入只读取当前快照真实评价数、评分、库存、新鲜度、来源状态和证据 ID；缺少快照或字段时保持候选，不推断排名、评价数或库存。

竞品详情把最早不可变快照明确标为基线、最新快照标为当前值，并同时展示已记录变化数和对当前竞品生效的全局/专属阈值。价格变化的币种按变化证据 ID 回查对应当前快照，变化时间使用该记录的 `changed_at`，不从最新快照推断历史币种。每条变化再作为处理时间轴节点，将基于该变化保存的影响结论、阈值告警通知状态和系统任务状态放在同一上下文；未命中阈值时明确显示未触发告警，不能把普通变化冒充告警。

页面首屏用紧凑的“竞争质量门 · 证据就绪”条汇总监控对象、真实快照和启用阈值，并直接暴露补齐竞品或阈值的下一步；该状态只说明工作区竞争证据链是否具备持续监控条件，商品是否通过竞争质量门仍以机会详情中持久化的竞争评分输入为准。创建入口统一为“添加竞品监控”，并按商品链接、市场信息、确认采集三步展示；步骤只组织既有 `market`、`product_url`、`title` 和可选 `opportunity_id`，前端长度、市场字符和机会 UUID 校验与服务端一致。详情通过 `latest_collection` 展示最近一次真实采集任务，排队或运行时每 2 秒自动读取详情，直到成功、阻塞或失败；首次进入页面也读取完整详情，不能把列表摘要误当作完整快照时间轴。详情保留价格与库存采集时间轴，并将变化、告警、任务和结论合并成独立处理时间轴；失败必须显示真实错误分类并提供重新采集。每条真实变化事件可直接创建高优先级人工验证任务，任务说明锁定竞品、变化事件、字段前后值、证据编号和采集时间，不覆盖原快照；创建后可直达任务详情。监控规则从商品详情分离到 `/competitors/monitoring-rules` 独立路由，专属规则入口通过 `competitor` 查询参数预选当前竞品；外部商品链接明确标注新窗口，移动端暂停与删除进入“更多操作”。列表搜索和当前竞品分别使用 `q`、`competitor` 查询参数恢复；写入口按服务端返回的 `competitor:manage` 和 `task:create` 能力显示，审计员只保留读取能力。使用帮助位于业务事实之后并默认折叠，避免遮挡首要判断和操作。

## 运行与隔离

所有业务表都以组织和工作区过滤；读用 `competitor:read`，写用 `competitor:manage`。审计员没有写权限。MySQL 5.7 是真实状态，Worker 使用租约、四次总尝试、1/5/15 分钟退避和死信；Redis 不保存业务真相。没有新增面板外生产服务。
