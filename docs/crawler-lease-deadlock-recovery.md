# 浏览器租约领取的死锁恢复

2026-10-18线上Amazon自动健康审计在11:49和12:16出现ER_LOCK_DEADLOCK。浏览器租约领取包含调度槽、档案、运行和审计事务；原实现回滚后直接失败，使本次健康检查受数据库瞬时死锁影响。并未证明全部超时或依赖失败均由死锁引起，浏览器页面稳定性和1688实机可用性仍需独立验证。

MySqlCrawlerRuntimeRepository.acquire仅对未提交事务中收到的ER_LOCK_DEADLOCK，在rollback成功且连接释放后重新领取。最多三次事务，重试前分别等待25、50毫秒；输入中的运行ID、租约ID、令牌哈希、幂等键、范围和原到期时间不变。重试只包括数据库事务，不重新执行浏览器、HTTP、商品写入或健康判定。

三次仍死锁则原样抛出原数据库错误。锁等待超时、普通SQL错误、业务租约冲突、权限/范围失败不重试；rollback失败或提交后读回失败不重试，避免把未知提交结果重放。保留原单机全局租约、档案锁、停用来源例外、幂等回放和审计规则。其他仓库方法没有扩大到通用重试。

定向测试模拟在运行记录插入后发生死锁，证明回滚内容未提交、连接在下一次事务前释放、同一运行只提交一次；另覆盖三次上限、原异常、业务冲突、锁等待、rollback失败和提交后错误。受控测试不等于线上死锁已根治，也不证明每日完整100品。

不新增环境变量、CLI、API字段、路由、数据库结构、数据库隔离级别、权限、Python或依赖。API调用方和Python payload不变。通过既有deploy-baota.py发布并由宝塔重载ai选品的API/Worker后生效，无需用户调参。若持续发生死锁，应继续依据实际事务证据调查；不能通过强制放行来源或增加商品计数签收。
