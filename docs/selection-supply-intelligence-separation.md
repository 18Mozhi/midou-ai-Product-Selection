# 货源报价不进入情报分析

## 依据与实现

用户要求先分析情报寻找Amazon商品，再通过LAN1688取得进货报价。2026-10-18北京时间04:46只读核验发现7787个1688趋势投影排在20个新RSS任务前。旧代码还把1688当作电商趋势来源、供应商名称映射为新闻发布方。这些入口现已删除；趋势补偿不再为新1688规范化证据创建任务。

历史已排队任务不删除、不改原始报价。Worker照常逐个领取租约，以既有空结果完成路径处理，每轮最多20个不支持的来源任务；若提前遇到有效任务，当轮继续正常分析。过期租约、完成失败传播、事务与历史补偿周期保留。历史供应商主题仍可读取，不伪装成已分析新闻。

报价继续由找货投影和自动评估读取，六个LAN节点、主品图片、进货价格、匹配、评分、Amazon发现与竞品详情不变。不以报价条数或旧主题数充当每日整链完成数。

## 验证与运行

新增3项回归在旧代码下失败，修改后相关35项通过，覆盖来源准入、排队排除、旧任务不调用投影、每轮20个上限及遇到有效任务立即继续。直接投影供应商的检查加强为明确拒绝，保留不写机会与下游任务的断言。

没有新API、事件字段、数据库结构、环境变量、依赖、权限、前端或Python输入；OpenAPI和环境示例无对应改动。20是内部单次空任务处理上限，不增加网络并发或源站频率。通过现有正式宝塔脚本发布并重启唯一Node项目ai选品加载Worker，无用户手动清队列步骤。回滚恢复旧代码，报价证据和历史任务保留。每日100整链、持续运行和全站重构仍未签收。

完整相关检查160项及找货补偿17项通过。MySQL5.7只读EXPLAIN核对编译后两条真实补偿SELECT，分别5和8行计划，无写入或临时表。文档、运行说明、路由及静态检查通过；正式发布与实际清理进度保留在本地核验收据，不能以本地检查代替真实运行验收。

## 单行领取与新情报优先

73c36818正式发布后的首轮真实观察：已有196个旧供应商任务完成为空、新供应商趋势任务为0，但队列记录了死锁。原领取查询对整个到期范围排序后FOR UPDATE，现改为先无锁选择候选，再仅按主键及组织/工作区加锁，并在锁内重新检查到期或过期租约条件；竞争者先获得租约时返回空，不覆盖租约或执行投影。不是修改全局数据库隔离级别或删除锁。

无锁候选查询优先RSS情报及带原有intelligence_product_discovery目标的Amazon关联查询，组内仍按可用时间和ID排序，其他任务按原顺序继续。优先依据来自同组织/工作区的规范记录、原始证据和采集子查询，不信任调用方请求头；原有情报来源与选主品证明继续在执行时验证。这样新情报不必先等数千条历史货源空任务全部结束。没有新增字段、配置、并发或服务。

后续179项相关检查通过，包含候选竞争失败不覆盖租约、仅对选定范围主键加锁和新情报优先。MySQL5.7真实现存任务的只读EXPLAIN显示候选范围读取不加锁，加锁阶段使用PRIMARY/const/1行。首次使用不存在的合成ID导致优化器直接消除查询，不能用该次结果声称索引失败或领取验证通过；已以真实行计划校正。没有执行并发生产写入测试，也不以计划证明死锁完全消失，仍需发布后的运行记录。
