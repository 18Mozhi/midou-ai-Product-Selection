# `/platform-admin/capacity` 页面审计记录

## 页面定位与证据

- 页面：容量边界；路由：`/platform-admin/capacity`；组件：`CapacityBoundaryCenter.vue`。
- 使用者：具备 `platform:operate` 的平台运维角色；平台超级管理员本地隔离测试账号已验证。
- 业务目标：只展示当前惠州 S0 单机的真实容量证据、停止线、最后连续通过档位、资源与归档/恢复事实，并在强确认后签认已完成的恢复演练。
- 数据链：页面 → 容量 GET/演练 POST → service/repository → `capacity_boundary_observations`、`capacity_boundary_drills`、`capacity_boundary_operations`、`platform_audit_events`。
- 截图：修改前 `output/playwright/platform-admin-capacity/before-desktop-1440.png`、`before-refresh-clears-snapshot.png`、`before-mobile-390.png`、`before-verifying-query-stuck.png`；修改后桌面与 390px 证据分别为 `after-desktop-1440.png`、`after-mobile-390.png`，异常链证据为 `after-refresh-preserves-snapshot.png`。
- 环境：隔离 MySQL 5.7、Redis、Node API、Node Worker、Python Crawler、Vite 与真实浏览器；未连接生产，未触发真实第三方采集、通知、支付或不可逆操作。

## 问题记录

### CAP-P1-001 刷新清空容量快照且请求无上限

- 类型/等级：功能、可靠性、性能 / P1。
- 复现：成功加载后锁住容量观测表并连续点击“刷新实测事实”。
- 预期：一个在途请求，旧快照保留，请求有界且失败可重试。
- 原实际：页面切换为 loading 并隐藏全部容量事实；按钮仍可点击，多个 GET 并发且无客户端/API 截止时间。
- 修复：页面单飞、序列、AbortController 和 15 秒上限；API 14 秒上限和断连取消；非权限失败保留快照，401/403 清除。
- 影响/API/数据：容量 GET 和读取审计；无数据库结构或业务阈值变化。
- 验收：真实 MySQL 锁等待、浏览器请求计数、页面截图和定向自动化均证明单飞、超时与快照保留。

### CAP-P1-002 双击签认可产生两条真实演练

- 类型/等级：功能、幂等、审计一致性 / P1。
- 复现：确认框输入准确短语，在 MySQL 写入受阻时双击“确认签认”。
- 预期：一次用户操作只产生一个 POST，并能安全重试不确定结果。
- 原实际：确认按钮未进入忙碌保护，两次 POST 各自生成随机 Idempotency-Key，写入两组演练、操作和审计。
- 修复：函数入口重复提交守卫、请求期间关闭确认框和禁用入口；一次操作复用稳定 Idempotency-Key，成功后才轮换。
- 验收：真实双击及定向 E2E 的 POST 计数为 1；数据库演练、操作和审计各只增加 1。

### CAP-P1-003 成功反馈被跟随刷新覆盖

- 类型/等级：交互反馈、可靠性 / P1。
- 复现：演练 POST 成功后让自动 GET 返回 503。
- 预期：签认成功、旧快照和刷新失败同时可见。
- 原实际：`load()` 立即清空成功消息，并以失败态替换容量页面。
- 修复：操作消息与刷新错误分离，跟随 GET 使用保留消息模式；失败不隐藏快照。
- 验收：真实签认和 E2E 均显示“已签认”、ready 快照及刷新告警。

### CAP-P1-004 查询参数可使页面永久停在核验态

- 类型/等级：功能、隐藏入口 / P1。
- 复现：打开 `/platform-admin/capacity?state=verifying`。
- 预期：查询参数不改变服务端事实，页面始终读取 GET。
- 原实际：组件依据查询参数初始化 verifying，并在 mounted 跳过读取，15 秒后仍无容量请求。
- 修复：状态只来自真实请求和当前操作；mounted 总是读取。
- 验收：原始卡死截图与修改后真实 GET/ready 快照形成对照。

### CAP-P2-005 未通过最低档时误显示规划上限完成

- 类型/等级：业务信息、UI / P2。
- 复现：最新真实容量证据 `measured_concurrency<5` 且没有下一档停止事实。
- 预期：明确固定并发 5 未通过，容量保持未验证。
- 原实际：指标说明和“下一档”都显示“规划上限已完成”，与 blocked/unverified 结论矛盾。
- 修复：按 `stop_reason`、`failed_next_concurrency` 和最低档位分别生成说明；缺失停止事实也失败关闭，不再冒充完成。
- 验收：真实 blocked 快照与双分辨率 E2E 均显示“固定并发 5 未通过”。

### CAP-P4-006 固定拓扑文案需保持语境明确

- 类型/等级：UI、可理解性 / P4。
- 当前证据：卡片显示“后端接口拓扑 / 单一 4101”，其语义是固定生产宝塔单上游，不是本地测试端口。
- 风险：脱离页首“惠州当前单机”语境时，测试或新运维人员可能把它误读为动态运行端口。
- 本批次处理：保留生产合同与原文案，避免把本地端口写入生产事实。
- 后续建议/验收：如产品允许，在字段标签增加“生产宝塔上游”，不动态暴露主机或端口详情；不得改变单上游合同。

## 页面级优化与验收标准

页面定位保持“容量结论与失败关闭”，主要操作是刷新，危险次要操作是签认已验证演练。保留规划与实测分离、全部四项性能指标、资源水位、归档/恢复、停止原因、finding、request_id 和单机声明；不删除、合并或把 5→10→20 变成任意测量。信息架构仍为结论 → KPI → 资源/韧性 → 告警 → 审计标识，仅增加刷新失败和操作结果两类独立反馈。加载、空、错误、超时、无权限、成功和失败必须可区分；桌面保持高密度双栏，390px 单列且不隐藏数字、风险或 CTA。

验收要求：一个在途 GET；浏览器 15 秒/API 14 秒；依赖错误脱敏；取消不提交成功读取审计；已有快照在非权限失败下保留；401/403 清空；签认双击只写一次且结果可幂等重放；成功消息不被刷新失败覆盖；`platform:operate`、API 字段、MySQL 5.7 表结构、容量阈值和单机拓扑不变。
