# 情报关联与 Amazon 主品发现

2026-10-17 用户的新目标覆盖旧规划中“普通新闻不得自动发现商品”的限制。新逻辑把关联判断作为可追溯的假设，再用实际采集结果确认商品身份，不能把模型假设写成销量增长或购买结论。

## 当前链路

1. 既有 `trend_projection_jobs` 领取当前有效规范化记录。对于尚未包含真实 Amazon 商品身份的情报，使用已配置的后端 OpenAI 兼容服务分析标题和摘要。1688 供货记录不重新作为需求情报。
2. `intelligence-product-v1` 分类为直接商品、需求驱动或无关；理由与原文引用必须存在，引用必须逐字来自输入。相关情报生成至多三个、每条至多 120 字符的 Amazon US 商品检索词；无关情报不能附带检索词。不推断精确销量、价格、广告费、评分或采购决定。
3. 分类、模型名及原始规范化记录 ID 写入 `trend.intelligence.associated` 事件和 Outbox，标记 `evidence_status=hypothesis`；每条检索词在同一事务内创建独立 Amazon 采集任务。内部目标为 `projection_type=intelligence_product_discovery`、`intelligence_source_record_id` 和 `query`。不接收模型提供的 URL、ASIN 或接口地址。
4. 搜索任务真正终态后，只为同任务的一个代表记录排队投影，避免每条结果各自生成一个主品。读取当前组织、工作区、任务内最多 30 条实际 Amazon 结果，验证 ASIN 与商品 URL 一致，排除显式标记为广告的条目。模型按标题相关性选择一个实际记录 ID，或者明确不匹配；模型不能新增商品。该选择是检索相关性判断，不是选品推荐。
5. 任务中的情报来源和检索词必须与同租户已持久化的关联事件吻合。选中的 Amazon 记录进入既有商品趋势与机会投影，关联原新闻的趋势证据；新增 `trend.intelligence.primary_selected` 假设事件。后续沿用主品详情、5–10 个独立竞品采集和有主图的 1688 找货链。采集阻断、空结果和缺失字段沿用原始状态，不伪装成功。

模型调用在事务外执行。投影前使用 `FOR UPDATE` 复核租约归属和有效期，失去租约不能发布任务。运行入口的趋势租约取原趋势租约与模型超时加 30 秒中的较大值。失败继续使用趋势任务既有四次尝试及 60/300/900 秒退避；无相关商品写 `succeeded_empty / intelligence_no_relevant_product`，模型失败按可重试性处理。无关情报仍正常进入趋势库。

来源审批、禁用、robots、验证码、熔断和限速仍由现有采集执行器检查，关联任务不会自动启用来源或绕过限制。禁用来源可以留下真实受阻任务，需由现有后台启用已核验来源并重试任务。没有 Amazon Provider 配置则原投影事务回滚并记录可重试错误。

## 配置与部署

复用已有 `AI_BASE_URL`、`AI_MODEL`、`AI_API_KEY`、`AI_TIMEOUT_MS`；地址和凭据只在后端受限配置中读取。没有新增环境变量、依赖、数据表、迁移、API 请求或响应字段，前端和 Python 本次不改。配置在启动时读取。

本地构建 Node 运行包后，按固定 `scripts/deploy-baota.py` 流程部署，并由宝塔重启 Node 项目：

`/www/server/panel/pyenv/bin/python /www/server/panel/script/restart_project.py nodejs ai选品`

## 已验证与未签收范围

- 单测覆盖字面引用、非法结构、检索词去重和上限、无关分类、实际主品引用、跨租户来源证明、响应体大小、超时、重试、失去租约、事务调度、新闻证据关联和后续三类采集目标。
- 真实局域网模型使用合成样本完成热浪需求驱动、棋赛无关和风扇/炒锅主品选择三项检查；不是生产情报或真实 Amazon 搜索验收。
- 线上 MySQL 5.7 对两段入队 SELECT、来源证明和候选记录读取共四段 SQL 做只读 EXPLAIN，通过。MySQL 不允许在只读事务中 EXPLAIN INSERT，因此只验证其原样 SELECT 部分，没有实际执行 INSERT。
- 旧监控规则门槛仍限制自动评分与推荐读模型；新情报主品没有命中监控规则时不会被伪装成建议采纳。通用品类评分、成本口径、这一旧门槛的完整替换、历史情报回填、真实来源恢复、连续自动采集、每日百品与全站 UI 重制仍需继续完成。
