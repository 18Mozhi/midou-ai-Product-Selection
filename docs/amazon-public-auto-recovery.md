# 匿名Amazon来源暂时性故障后的自动恢复

## 实际依据

2026-10-18生产已取得67个不同ASIN的真实价格，但来源在14:43因network_error再次熔断。原自动恢复只覆盖RSS，Amazon不能自然恢复，后续主品、竞品任务因此停止。手工真实双探针在14:58通过：搜索10条、同ASIN B0F6FT397Y详情26.99 USD、美国观察邮区验证通过，才按原恢复流程关闭熔断。期间三次健康检查遇到ER_LOCK_DEADLOCK并保持熔断；没有强制清除熔断、修改数据库权限或把健康成功当整链完成。

## 执行边界

既有Node API进程增加一个有界恢复轮询，复用RSS恢复的单次在途、停机等待、真实健康检查和原恢复事务。仅处理已启用、条款有效、public_page的amazon_product，且熔断原因为network_error、timeout或rate_limited。熔断与最近检查都经过冷却、没有更新的blocked检查，并确实存在既有专用系统用户创建的待执行Amazon任务，才允许一轮检查。没有任务则不探测；停用来源、条款撤销/过期、验证码、登录、解析漂移或其他故障不自动解锁。

健康范围来自该系统用户已有任务的真实组织和工作区，并在探针前再次确认用户、组织、同组织工作区活动且任务仍待执行。内部automaticCollectionTaskId仅由恢复器生成；HTTP请求不能注入它，也不能替换已登录身份。系统用户沿用AUTOMATIC_SOURCE_SYSTEM_ACTOR_ID，不创建账号、不赋予管理员角色、不借用用户登录会话。普通人工健康检查的会话授权保持。

只使用既有canonical匿名空浏览器档案、既有来源代理及邮区。自动探针没有人工健康页“检查已停用来源”的租约特例；来源中途停用不能使用该特例继续探针。真实搜索和同品详情均ready且检查晚于熔断，才调用原recoverProvider；该事务重新核对来源版本、条款、同一熔断事件和错误类型，继续写原操作及平台审计。失败保持熔断，冷却后再检；没有新业务事实写入、任务状态篡改或假数据。

## 使用和配置

后端新参数AMAZON_PUBLIC_AUTO_RECOVERY_ENABLED默认true；AMAZON_PUBLIC_AUTO_RECOVERY_POLL_MS默认60000；AMAZON_PUBLIC_AUTO_RECOVERY_COOLDOWN_MS默认300000。分别允许1000–3600000ms轮询、1000–86400000ms冷却，越界启动失败。生产还必须已有匿名档案和有效专用系统用户。只在宝塔本项目受限环境调整，修改后重启Node API；Worker、Python不读取新参数，前端没有新入口或字段。发布仍用本地deploy-baota.py和宝塔固定目录，不增加服务。

API日志事件amazon_public_auto_recovery仅在状态变化时记录；失败记录固定错误标签，不输出代理或凭证。没有新增路由、数据库迁移、权限授予或依赖。原RSS默认查询和行为保持，原Amazon采集节奏、重试、验证码、来源条款和六节点1688不变。

## 验证与未签收事项

定向检查覆盖冷却参数、真实任务范围、私有上下文、HTTP伪造隔离、ready前不恢复、原版本/条款/熔断事件复核、单轮在途与关闭等待。生产SQL必须另做MySQL5.7只读验证；发布后查看版本、API轮询与来源状态。不得为验收主动伪造生产网络故障或改数据库熔断状态；自然发生一次暂时性故障并成功自动恢复前，真实自动恢复验收仍待完成。每日100个不同主品的完整流程另行验收。

本轮64项配置、适配器、匿名档案、RSS与Amazon恢复相关检查通过；包含HTTP伪造隔离和自动探针不使用停用来源租约特例。生产MySQL5.7只读执行候选SQL成功（来源已正常关闭熔断，候选0），实际系统待执行任务的范围复核通过，错误用户绑定返回0。未修改来源、任务或数据库状态来制造验收。
