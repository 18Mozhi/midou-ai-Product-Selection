# 采集领取的工作区公平轮转

## 真实问题与方案选择

2026-10-19 00:18 只读审计：最近一小时 70 次领取全部属于同一有效工作区，米兜 341 个高优先级发现任务未被领取。另有 344 个同档任务处于第三个有效工作区。三个范围都通过原 active scope、来源就绪和尝试次数条件；旧全局时间顺序与完成优先不能约束工作区等待时间。

保留有效 critical/high/normal/low 优先级及已审计情报摄取从 normal 提升 high 的规则；同一有效档位先选最近最久未获领取的组织/工作区，未领取过的范围先行，再在选中范围内应用既有摄取、完成通道和 available_at/id 顺序。没有指定米兜或任何特定组织优先。

最近领取只来自已提交 collection.task.leased / actor_type=worker 事件，组织与工作区共同关联。采用一次 MAX 聚合的物化派生表，两处候选只读取 collection_tasks.*，不把关联字段加入任务合同。事务回滚不会留下领取事件，重新启动不抹去范围的领取历史。既有进程每 21 次领取的本地 FIFO 轮次继续保留，未改为持久化计数。

初始逐候选及单层分组相关子查询都触发原 3 秒查询上限，未提高上限。聚合方案在实际 MySQL 5.7 下候选领取约 342ms、入队约 383ms；现有 scope_time 索引扫描约 11 万事件，未增加表或索引。这是当次读证据，不是长期性能或吞吐 SLA。另一个双层范围清单方案约 386ms，没有优于聚合，未采用。

## 保留与边界

- 只调整 queueReady/claim 候选排序；选中后的主键、组织、工作区、状态、来源与次数锁定复核仍在原事务中执行。
- 来源停用、open 熔断、非活动/不匹配范围和耗尽任务不因此获得领取。原 typed 1688 acceptance 例外不变。
- Worker/Crawler/每来源单实例租约、原租约配置、4 次尝试、退避、全局积压预算和独立调度资源门不变。
- 不归档其他有效组织，不改已有任务优先级、时间、结果、次数或历史事件，不合并、搬运或跨范围复用商品事实。
- 无新 API 字段、数据库结构、依赖、配置开关、前端或 Python 输入变化。OpenAPI 只更新既有 priority 的调度说明，env.example 只更新注释。
