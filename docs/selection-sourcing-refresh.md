# 自动找货按来源周期刷新

## 真实问题与交付边界

2026-10-20 06:50同工作区Cooling、iPhone16和Miracase的找货任务均已成功，搜索记录均为completed_with_warnings；1688来源schedule_minutes=30，三条结果均已过期。原enqueueMissingAutomaticDownstream只补没有任何历史找货任务的商品，成功结果永不触发刷新。这与持续获取最新数据的要求不符。

本次仅补缺少正数当前进货价、waiting_evidence且原因为high_confidence_1688_match_missing或automatic_cost_scope_mismatch的待处理自动商品。已经完成或已有当前进货价的商品不在本次刷新范围；整链每日100个仍未验收，不能把刷新次数、候选数或旧商品重评计为新增完成数。

## 运行合同

- 读取1688来源现有采集周期schedule_minutes，到最后成功投影updated_at加该周期后才允许新搜索；不新增环境变量、周期默认值或服务。
- 必须为同组织/工作区、有效自动主品，具备原正式Amazon详情证据、原图和原始标题。原趋势标题证据缺失时，仅从同主品最新正式详情的精确规范化记录读取标题，不使用可编辑机会名。
- 保留enabled、authenticated_browser、条款批准/有效期、非open熔断、活动租户、真实worker自动生产事件、原任务/子查询/搜索身份检查。失败或blocked历史任务不属于本次成功结果刷新；原熔断恢复逻辑保留。
- 仅最新搜索允许刷新。存在更新的手工/自动搜索、同商品未结束找货任务、已有正数当前进货价或原1000全局活动采集软门限达到时不创建新任务。门限仍为共享软检查，不宣称跨生产者原子容量预留。
- 普通只读扫描按旧结果时间排序；逐条同主键/租户解析正式主品，缺图或缺正式详情不会挡住后续商品。避免对整个候选集的复杂主品表达式做相关排序。候选扫描不锁历史范围；随后锁原搜索主键、机会主键，重新检查全部条件、读取当前图片标题，事务内新建搜索、原自动高优先级采集任务及seed事件。
- 新搜索保留原始搜索、报价、证据、任务和关联指针。仍用supplier-keywords-v2、sourcing_search、主品image_url及sourcing.collection.auto_scheduled，六节点传输与报价筛选不变。seed事件沿用原结构，补充previous_search_id和refresh_reason用于追溯。
- 成功原下游调度后，下轮优先尝试一次货源刷新；成功刷新后回到原下游。若没有刷新候选则继续原下游，原下游无工作时也可补一次刷新。原Amazon发现/详情内部轮换保持；不是保证原缺失补采/熔断修复每一轮都优先。失败不切换轮次。

## 使用与部署

后台采集来源中调整1688来源现有“采集周期”，下次调度动态读取，不必重启即可读取周期新值。代码发布需要使用项目既定本地deploy-baota.py并由宝塔重启Node项目ai选品；没有新增生产进程或Python合同。前端、API字段/路由/权限、数据库结构、依赖、模型/评分和报价置信规则未改。
