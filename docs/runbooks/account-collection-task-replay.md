# Collection task history and replay after account cutover

Platform list and detail require matching native and sealed task ownership. Summaries show the account ID; legacy organization/workspace filters are not accepted in account mode. Keep task, attempt, event, dead-letter and trace IDs. Detail does not return lease tokens, credentials or internal query inputs.

The existing `collection:replay` permission, origin check and reason requirement remain. Apply replay only to a valid open dead letter tied to the original attempt. The new task and its subqueries, events and delivery keep the source account and ownership reason, not the operator's account. Record the real operator separately. The original transition, exact dead-letter update, child ownership and receipt commit atomically.

The same key and reason return the already committed task. Following a concurrent commit, the receipt and returned graph use current reads, even if a previous read opened an older snapshot. A changed reason, missing or foreign subquery, or owner mismatch returns 409 without a second task. No automatic replay, retry-policy, limit or scheduled task change.

The account Worker checks native and sealed task ownership before claiming, and locks the original subqueries before consuming an attempt. Missing or foreign subquery ownership is not runnable. The account, attempt and active lease are rechecked when starting, renewing or completing native work. Queue events and deliveries keep the task's account; a missing or mismatched native owner rolls the transition back. Redis readiness and lease keys use the verified account and original task ID. Existing priority, retry and overflow limits are unchanged.

The retired runtime retains the existing hot maintenance contract. The production collection Worker, browser admission and maintenance CLI share the same MySQL advisory fence and pause marker. A pause blocks new collection task claims and standalone browser admission. Browser children can still drain only for their exact running parent and matching live Worker lease; heartbeats and completion of issued leases continue. A maintenance denial does not record a provider health failure. No new environment variable or threshold: use the installed `scripts/collection-claim-maintenance.mjs status | pause UUID | resume UUID` from the fixed backend with its two BaoTa environment files through SSH. Resume only the UUID that owns the pause.

Verify with `npm run build:api`, `npm run build:worker`, `npm run typecheck:web`, and the collection task, replay, scheduling, history and Redis tests in the feature map. The approved BaoTa coordinator installs and starts the API and Worker with the built frontend; there is no separate flag or manual restart. After release, verify historical tasks through the platform without triggering an unsolicited replay.
