# 连续选品的数据库阻塞修复

## 已观察到的问题

2026-10-18 生产 Worker 存活，但采集队列连续六次在 recover_expired/task_candidates 报 ER_LOCK_DEADLOCK，进入队列熔断。实际回收查询没有符合到期条件的任务，MySQL 5.7 执行计划仍从 idx_collection_task_schedule 按状态扫描约 117 行；原 FOR UPDATE 会锁定扫描范围。未取得全局死锁图，不能指认某一具体对手事务或宣称所有死锁已解决。

同一业务账号还有五条相同代码的主品证据 SELECT，均指向同一机会，最早运行超过 80 分钟。原查询在 69 条历史链接上相关求值主品身份；新连接设置 3000ms 诊断上限后仍超时。单独解析身份约 200ms，原型先物化一次身份后约 2.1 秒返回。这些是当前数据快照的测量，不是性能承诺。

## 修改

过期回收及重试溢出先读取候选，不对候选状态范围加锁。真正处理前按任务 ID、组织、工作区加主键行锁，并重新校验状态、过期时间或重试次数。候选期间已续租或已变更的任务跳过；重试、死信、事件、outbox、全局租约清理和批次事务回滚规则不变。

automaticPrimaryEvidenceSql 将原主品身份表达式放入限定单机会的派生表，LIMIT 1 阻止 MySQL 5.7 合并，从而每次查询只计算一次身份。三个参数顺序保持机会、组织、工作区；原链接身份、当前版本、原始地址证明、状态、币种、价格和排序均保留。详情证据 SQL 及主品选择规则本身不改。

## 验证

四项回收回归在旧代码失败，在修改后通过，覆盖零候选、并发续租、当前重试次数及溢出任务变更。tests/unit/automatic-primary-query.fixture.mjs 在真实 MySQL 5.7 上仅使用只读派生行，八组用例共 24 次读取验证新旧事实一致：旧链接与新版本、隔离、跨工作区、ASIN 变化、无效地址、多个当前版本、来源停用状态、无当前记录。

同一只读一致性快照内，真实慢查询机会、另一个当前机会及跨工作区负例分别与“原身份表达式单独解析，再执行原事实查询”的结果完全一致；改后约 2102/3/2ms。对慢查询实例，旧完整查询已确认超出 3000ms。单元和只读检查不替代部署后的持续采集验证。

## 发布与运维

无新增依赖、环境变量、API 字段、权限或数据库迁移；OpenAPI、环境示例和 Python 输入无变化。发布使用既有固定宝塔部署命令，Node API/Worker 需要重启加载；部署脚本统一重启的 Python 服务协议不变。没有新增调节开关。

旧 MySQL SELECT 不会因为前端恢复或 Node 重启就必然立即结束。新代码上线后，只能用 product_scout 账号确认旧代码完整查询前缀、原机会作用域、只读语句和超过 60 秒的运行时间，再对仍匹配的历史查询执行 KILL QUERY。不得终止其他语句、事务、用户或数据库，不修改数据库权限、隔离级别或全局超时。操作 ID、时间、前后状态保存在受限验证回执中。

最终仍需观察回收队列是否继续死锁、主品重试是否被正常领取、自动评分是否产生真实输入，以及整链完成事件。每日 100 个商品尚未验收。
