# 《安全与数据隔离风险报告》

## 已验证控制

- HttpOnly 会话、MFA、会话撤销、动作 token 单次消费。
- 组织/工作区上下文、角色能力、data scope、resource grants 四层裁决。
- 平台角色与组织业务身份分离；菜单隐藏不是授权依据。
- 凭证/Client/Webhook 密钥加密存储、秘密只显示一次、日志脱敏。
- request_id/trace_id、幂等记录、版本冲突、审计/outbox。
- 短期下载授权、证据路径约束、开放平台 nonce/签名/配额。

## 风险

### SEC-001（P1）长尾接口跨租户验证证据不完整

- 模块：257 个 OpenAPI 操作；类型：数据隔离。
- 描述：核心 repository/路由有跨租户测试，但不能证明每个长尾管理操作都做过真实跨租户请求。
- 复现：以组织 A 会话访问组织 B 的 path/body/query/resource ID。
- 预期：404/403 按合同返回，无存在性和字段泄露，产生安全审计。
- 实际：核心业务通过；全 operation manifest 缺失。
- 证据：API-001；涉及文件/接口/数据：全 API 和租户表。
- 影响：全租户；严重度：P1。
- 建议：生成跨租户矩阵并在 CI 对每个 operationId 绑定用例。
- 验收：所有带租户资源的 operation 都有 A→B、B→A、无上下文用例。

### SEC-002（P1）真实第三方凭证生命周期未完成

- 模块：Amazon/1688/网页登录采集；类型：凭证安全。
- 描述：本地加密、轮换、撤销和租约合同通过，但真实 Cookie 过期、验证码、风控、重启恢复无全周期证据。
- 影响：凭证泄露或错误复用；建议：只用测试账号、隔离档案、最小权限、人工验证码；验收同 CRAWL-001。

### SEC-003（P2）Webhook 目标 SSRF 与真实接收端未实测

- 模块：开放平台；类型：出站访问。
- 描述：合同包含 URL 校验/签名/nonce，但真实 DNS 变化、重定向和内网地址阻断需集成环境验证。
- 建议：解析后 IP 策略、每次重定向复核、出站 allowlist/denylist、响应大小与超时限制。
- 验收：localhost、RFC1918、link-local、DNS rebinding、重定向链全部拒绝并审计。

### SEC-004（P2）单机备份不等于灾备

- 模块：文件/数据库恢复；类型：可用性与数据保护。
- 实际：同机加密目录和隔离恢复库；没有异地、磁盘级或机房级灾备。
- 建议：在当前授权边界内明确 RPO/RTO，不宣称不存在的能力；未来扩展需另行审批。
- 验收：每次发布前备份校验和隔离恢复演练有日志。

### SEC-005（P2）日志/导出可能携带隐私

- 模块：日志、审计、报表、平台数据；类型：隐私。
- 建议：字段 allowlist、公式注入防护、下载授权短期化、导出原因和范围审计、保留期执行。
- 验收：密码/Cookie/Token/密钥不进入响应、日志、截图或导出；CSV 公式前缀安全处理。

## 结论

安全门禁和核心租户隔离已具备，但 SEC-001/002 使“全接口、全第三方、全生产安全通过”不成立。
